## 2. خطة التطوير المقترحة

### المرحلة الأولى: الاستقرار والموثوقية (أولوية عالية)

#### 2.1.1 إزالة الكود الميت (Dead Code)
- **`lib/ai-orchestrator/src/execution/phase-runner.ts`** — هذا الملف "وهمي" بالكامل (يصف المهام فقط، لا يولّد كود). يبدو أنه legacy غير مستخدم في pipeline الفعلي (`execution-engine.ts` يستخدم `BatchFileGenerator` مباشرة).
- **الإجراء:** حذفه أو توثيق أنه غير مستخدم، لتجنب الالتباس.

#### 2.1.2 تحسين معالجة الأخطاء في BatchFileGenerator
- إضافة retry logic أكثر ذكاءً (distinction بين 402/429/timeout)
- logging أفضل للأخطاء
- metrics لعدد الملفات المولّدة ونسبة النجاح

#### 2.1.3 تحسين stage 15 (Auto Debug)
- التشخيص الحالي يعرض فقط `fc.detail?.slice(0, 80)` — يمكن تحسينه ليعرض استراتيجية إصلاح حقيقية

### المرحلة الثانية: تجربة المستخدم (UX)

#### 2.2.1 تحسين واجهة الشات
- إضافة مؤشر تقدم بصري لكل مرحلة من المراحل الـ 17
- إضافة زر "إيقاف" أوضح أثناء التنفيذ
- إضافة تاريخ كامل قابل للبحث في كل محادثة
- إضافة إمكانية تعديل الرسائل السابقة (partial — موجود فقط لآخر رسالة)

#### 2.2.2 تحسين المعاينة (Preview)
- المعاينة الحالية تخدم الملفات الثابتة — يمكن إضافة hot-reload
- إضافة معاينة الكود (code viewer) مع syntax highlighting
- إضافة diff view قبل/بعد الإصلاح

#### 2.2.3 تحديثات الوقت الحقيقي
- إضافة WebSocket أو SSE لإشعارات الوقت الحقيقي
- إشعار المستخدم عند اكتمال البناء حتى لو غادر الصفحة

### المرحلة الثالثة: التوسع الوظيفي (Features)

#### 2.3.1 نشر المشاريع (Deployment)
- **الحالة الحالية:** المشاريع تُبنى محلياً فقط (dist/)
- **المقترح:** إضافة نشر فعلي إلى:
  - Vercel (للتطبيقات الثابتة/Next.js)
  - Railway (للتطبيقات الكاملة)
  - Netlify (بديل)
- **التنفيذ:** استخدام API keys من المستخدم + deployment route في api-server

#### 2.3.2 تكامل Git/GitHub
- **الحالة الحالية:** موجود `lib/github/` و routes في `repositories.ts`
- **المقترح:** إضافة:
  - إنشاء repository تلقائي للمشروع المولّد
  - commit + push تلقائي
  - PR creation للمراجعة

#### 2.3.3 قوالب وقئات بدء (Templates & Starter Kits)
- إضافة قوالب جاهزة (React app, Next.js, Express API, etc.)
- هذا يسرّع التوليد (BatchFileGenerator يبدأ من قالب بدلاً من الصفر)

#### 2.3.4 دعم تقنيات إضافية
- **الحالي:** React + Express + Drizzle
- **المقترح:** إضافة:
  - Vue/Svelte support
  - Python/FastAPI support
  - Go support
  - Static site generators (Astro, Eleventy)

### المرحلة الرابعة: الأداء والتوسع (Performance & Scaling)

#### 2.4.1 تخزين المشاريع
- **الحالة الحالية:** الملفات على القرص المحلي (`PROJECT_DIR_BASE`)
- **المشكلة:** على Railway/Replit، التخزين المؤقت قد يُفقد
- **المقترح:** 
  - تخزين الملفات في S3/R2
  - أو تخزين في PostgreSQL (base64)
  - أو persistent volume mounts

#### 2.4.2 ذاكرة التوليد (Generation Cache)
- **المقترح:** caching لنتائج LLM المتشابهة
- تقليل استدعاءات LLM المتكررة لنفس الـ prompts
- تقليل التكلفة وزمن الاستجابة

#### 2.4.3 موازنة الحمل (Load Balancing)
- **الحالة الحالية:** 6 طبقات fallback للمزودين
- **المقترح:** 
  - load balancer ذكي يوزع الطلبات على المزودين
  - rate limit handling أفضل
  - cost optimization (اختيار الأرخص المتاح)

#### 2.4.4 تنفيذ متوازي (Parallel Execution)
- **الحالة الحالية:** BatchFileGenerator يعمل بالتسلسل (9 دفعات)
- **المقترح:** تنفيذ بعض الدفعات بالتوازي (مثلاً frontend + backend معاً)

### المرحلة الخامسة: الأمان والحوكمة (Security & Governance)

#### 2.5.1 إدارة المفاتيح (Key Management)
- **الحالة الحالية:** `provider-manager/key-vault.ts` + `secrets-center.ts`
- **المقترح:** 
  - تشفير المفاتيح at rest
  - rotation تلقائي للمفاتيح
  - audit log للوصول للمفاتيح

#### 2.5.2 حدود الاستخدام (Rate Limiting)
- **المقترح:** rate limiting per-user لمنع الإساءة
- quotas يومية/شهرية للمستخدمين

#### 2.5.3 فحص الكود المولّد (Security Scanning)
- **المقترح:** فحص الكود المولّد للثغرات الأمنية قبل النشر
- dependency vulnerability scanning

#### 2.5.4 عزل التنفيذ (Execution Isolation)
- **الحالة الحالية:** `npm install` و `build` تعمل في نفس بيئة الخادم
- **المقترح:** 
  - Docker containers لكل مشروع
  - أو sandboxed execution environment
  - هذا أكثر أماناً ويمنع تأثير المشاريع على بعضها

### المرحلة السادسة: المراقبة والتحليلات (Monitoring & Analytics)

#### 2.6.1 مراقبة الأداء
